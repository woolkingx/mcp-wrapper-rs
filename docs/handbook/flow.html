Flow

State Movement

Every JSON-RPC line is classified, projected through event_plane, then executed by the current port owner. The mount table chooses cache, local, control, lifetime, refresh, or pass-through behavior; normal and daemon mode keep their own stdout/session mechanics.

Startup builds cache by spawning a temporary backend, performing initialize, sending initialized, querying supported list methods, then killing the temporary backend in normal mode. Daemon mode keeps the initialized backend alive and broker-owned.

The initialize request sent to the backend uses today's YYYY-MM-DD protocol version and stores the backend-negotiated response version unchanged. Backend list pagination is drained during cache build and refresh; frontend cached list responses do not expose backend cursors.

Pass-through calls generate backend IDs, restore client IDs on response, and keep the backend alive until idle reaper or shutdown. Normal mode and broker mode keep pass-through calls serialized, but the client read loop stays active while a backend call is in flight.

Request lifetime flow is enter -> register channel map id -> register lifetime index -> progress/cancel/timeout decision -> response or discard -> remove index. The backend pending channel map owns completion; process exit atomically drains all pending senders in that generation so requests without a configured timeout still terminate. lifetime owns id/token/session lookup only, and daemon client indexes use the complete (session_id, raw_client_id) identity without a raw-id fallback.

N:1 sharing is a table join: one broker-owned Wrapper process has many Session rows, and each active Request row joins one Session to the shared backend wire identity. Session-active and backend-active counts are derived by filtering Request rows. A backend peer request selects the sole eligible active Session row under the current serialized backend policy, then inserts a session-complete PeerRequest row; no active_peer_session pointer or independent active-call counter owns that decision.

Cancellation flow is explicit: client cancel for an active client-origin request is resolved within the originating session, translated to the backend id, removes the pending channel sender, writes a backend cancel notification, and discards any late backend response. Peer request cancel/progress is allowed only for the active peer request token/id in the same daemon session.

mcp.wrapper calls are not pass-through calls. Runtime or broker code recognizes tools/call for the reserved tool name, builds the current tools context, and calls tools::invoke. tools validates the action and params, then calls the existing backend/cache owner APIs through object methods and returns a unified readback envelope.

Server-to-client backend requests are request-scoped. A backend peer request is relayed to the active client, the client's JSON-RPC response is written back to the backend, and the backend's final response returns to the original client request ID. Broker mode rejects unassociated backend requests instead of broadcasting them.

Backend intelligence follows a hook/observe chain: typed backend event, backend generation state, explicit wrapper hook, discovery cache refresh by generation, then notification or status evidence after readback. Backend stdout events are classified as notifications, peer requests, unmatched responses, or process exits before runtime or broker code acts on them.

The backend stdout reader never waits for a runtime consumer acknowledgement. It emits notifications in read order and continues reading responses, because a consumer may itself be awaiting that response. Cancelled and timed-out backend IDs remain suppressed for the lifetime of the backend generation; suppression correctness is not evicted by a cache-size cap.

The standard notifications/resources/list_changed signal invalidates both resources/list and resources/templates/list; MCP defines no separate resource-template list-changed notification. In daemon mode, successful mcp.wrapper backend.refresh and backend.restart actions finish cache refresh and readback before broadcasting the standard tools, prompts, and resources list-changed notifications. Failed or non-mutating actions emit none.

One refresh operation owns one absolute deadline across every discovery key and pagination page. It builds a transient candidate while the committed snapshot remains readable, rejects JSON-RPC error envelopes and malformed list results, and commits all selected rows in one write only if the backend generation and base cache epoch still match. Refresh construction is serialized per cache, so an older invalidation cannot finish after and overwrite a newer committed truth. Any failed, incomplete, stale, or generation-crossing candidate preserves the complete previous snapshot and emits no list-changed notification.
