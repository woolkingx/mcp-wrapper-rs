MCP Spec Reference

Purpose & Scope

This chapter records the official Model Context Protocol requirements that an stdio proxy/wrapper must honor. It is the upstream contract: what the spec demands. It is a reusable reference, version-pinned and citable, not a status report. Our own compliance state and remediation work live in docs/plan/2026-06-22-mcp-spec-compliance-audit.md, not here.

Reading split: Schema owns our legal shapes; this chapter owns the MCP spec's requirements on a proxy.

A. Lifecycle & Version Negotiation

Source: 2025-06-18 basic/lifecycle.

LevelRequirementSection
MUSTInitialization MUST be the first interaction between client and server.Initialization
MUSTClient MUST send an initialize request with protocolVersion, capabilities, clientInfo.Initialization
MUSTServer MUST respond with protocolVersion, capabilities, serverInfo.Initialization
MUSTAfter successful init, client MUST send notifications/initialized.Initialization
SHOULD NOTClient SHOULD NOT send non-ping requests before the server responds to initialize.Initialization
SHOULD NOTServer SHOULD NOT send requests other than ping/logging before receiving notifications/initialized.Initialization
MUSTClient MUST send a protocol version it supports; SHOULD be the latest it supports.Version Negotiation
MUSTIf the server supports the requested version, it MUST respond with the same version.Version Negotiation
MUSTIf not supported, the server MUST respond with another version it supports (SHOULD be its latest).Version Negotiation

B. JSON-RPC 2.0 Conformance

Source: 2025-06-18 basic/index § Messages; schema.ts.

LevelRequirement
MUSTAll messages MUST follow JSON-RPC 2.0.
MUSTRequests MUST include a string or integer id.
MUST NOTThe request id MUST NOT be null.
MUST NOTThe request id MUST NOT have been previously used by the requestor within the same session.
MUSTResponses MUST echo the same id as their request.
MUSTA response MUST set exactly one of result / error, never both.
MUSTError codes MUST be integers.
MUST NOTNotifications MUST NOT include an id.
MUST NOTReceivers MUST NOT send a response to a notification.

Reserved error codes (schema.ts):

CodeConstantMeaning
-32700PARSE_ERRORInvalid JSON received.
-32600INVALID_REQUESTJSON is not a valid Request object.
-32601METHOD_NOT_FOUNDMethod does not exist / is unavailable.
-32602INVALID_PARAMSInvalid method parameters.
-32603INTERNAL_ERRORInternal JSON-RPC error.

Batch removed: 2025-06-18 defines JSONRPCMessage as a union of single request / notification / response / error only. No array/batch form exists; a proxy must not emit or coalesce batch arrays.

C. Request Lifetime (Timeouts)

Source: 2025-06-18 basic/lifecycle § Timeouts.

LevelRequirement
SHOULDEstablish a timeout for all sent requests.
SHOULDOn timeout, issue notifications/cancelled for that request and stop waiting.
SHOULDAllow timeouts to be configured per request.
MAYReset the timeout clock on receiving a notifications/progress for the request.
SHOULDAlways enforce a maximum timeout regardless of progress, to cap a misbehaving peer.

D. Cancellation

Source: 2025-06-18 basic/utilities/cancellation.

LevelRequirement
MUSTCancellation MUST reference a request previously issued in the same direction and believed in-progress.
MUST NOTThe initialize request MUST NOT be cancelled by clients.
SHOULDReceiver SHOULD stop processing, free resources, and send no response for the cancelled request.
MAYReceiver MAY ignore a cancel for an unknown / completed / non-cancellable request.
SHOULDSender SHOULD ignore any response that arrives after it sent the cancel.
MUSTBoth parties MUST handle the race where cancel arrives after the response was sent.
SHOULDInvalid cancellations (unknown id, already done, malformed) SHOULD be ignored.
{ "method": "notifications/cancelled",
  "params": { "requestId": "123", "reason": "User requested cancellation" } }

requestId is RequestId = string | number (schema.ts CancelledNotification).

E. Progress

Source: 2025-06-18 basic/utilities/progress.

LevelRequirement
MUSTProgress tokens MUST be a string or integer (ProgressToken = string | number).
MUSTProgress tokens MUST be unique across all active requests.
MUSTThe progress value MUST increase with each notification, even if total is unknown.
MUSTProgress notifications MUST only reference tokens from an active, in-progress request.
MUSTProgress notifications MUST stop after completion.
SHOULDBoth parties SHOULD track active tokens and rate-limit to prevent flooding.

Token location: params._meta.progressToken of the request (schema.ts Request).

{ "method": "notifications/progress",
  "params": { "progressToken": "abc", "progress": 1, "total": 10, "message": "..." } }

Source: 2025-06-18 basic/utilities/ping.

LevelRequirement
MUSTThe receiver MUST respond promptly with an empty result {}.
SHOULDPeriodically issue pings to detect connection health; frequency SHOULD be configurable.
SHOULDAvoid excessive pinging; treat ping timeouts as connection failures.
req:  { "id": "123", "method": "ping" }
resp: { "id": "123", "result": {} }

G. Transport — stdio

Source: 2025-06-18 basic/transports § stdio.

LevelRequirement
MUSTJSON-RPC messages MUST be UTF-8 encoded.
MUST NOTMessages MUST NOT contain embedded newlines (they are newline-delimited).
MUST NOTThe server MUST NOT write non-MCP content to stdout.
MUST NOTThe client MUST NOT write non-MCP content to the server's stdin.
MAYThe server MAY write UTF-8 logs to stderr; clients MAY capture/forward/ignore them.
SHOULDClient shutdown sequence: close stdin → SIGTERM → SIGKILL.
SHOULD NOTDisconnection SHOULD NOT be interpreted as cancellation; cancel requires an explicit notifications/cancelled.

The explicit "disconnect is not cancellation" wording sits in the Streamable HTTP section; the same principle holds for stdio because cancellation requires an explicit notification.

H. Capabilities & Feature Gating

Source: 2025-06-18 basic/lifecycle § Capability Negotiation; server/*.

LevelRequirement
MUSTBoth parties MUST only use successfully negotiated capabilities.
MUSTServers that support tools MUST declare the tools capability.
SHOULDA server declaring listChanged SHOULD send the matching */list_changed notification on change.

Gating map: tools.listChanged, prompts.listChanged, resources.listChanged each gate their list_changed notification; resources.subscribe gates resources/subscribe and notifications/resources/updated.

The resources capability has one list-change signal: notifications/resources/list_changed. Because both resources/list and resources/templates/list are discovery views of that capability, the wrapper refreshes both views when this signal arrives. There is no notifications/resources/templates/list_changed method in the MCP schema.

Proxy clarification: "only negotiated capabilities" governs the backend's capabilities. A proxy declaring a capability it owns and fully implements itself (e.g. the wrapper's own control tool) is permitted — the spec allows a party to offer a capability it implements. Misrepresenting the backend's capabilities (advertising what the backend lacks, or suppressing what it declared) is the violation, not owning a self-implemented one.

I. Pagination

Source: 2025-06-18 server/utilities/pagination.

LevelRequirement
MUSTClients MUST treat cursors as opaque: do not parse or modify.
MUST NOTClients MUST NOT assume a fixed page size.
MUST NOTClients MUST NOT persist cursors across sessions.
SHOULDServers SHOULD provide stable cursors and handle invalid cursors gracefully.
SHOULDA missing nextCursor SHOULD be treated as end of results; support paginated and non-paginated flows.
SHOULDInvalid cursor SHOULD return -32602 (invalid params).

Paginated operations: resources/list, resources/templates/list, prompts/list, tools/list. Cursor = string (opaque).

J. _meta & Reserved Key Names

Source: 2025-06-18 basic/index § General fields § _meta.

A valid _meta key has an optional prefix and a name.

  • Prefix (if present): a series of dot-separated labels followed by a slash (/). Labels start with a letter, end with a letter or digit; interior chars may be letters, digits, hyphens.
  • Reserved: any prefix whose label sequence contains modelcontextprotocol or mcp as a label segment is reserved for MCP. Examples: modelcontextprotocol.io/, mcp.dev/, api.modelcontextprotocol.org/, tools.mcp.com/.
  • Name: unless empty, MUST begin and end with an alphanumeric character; may contain hyphens, underscores, dots, alphanumerics between.

Critical scope distinction. The reserved-prefix rule applies only to keys inside the _meta object. The spec imposes no reserved-name or naming-pattern restriction on tool names, method names, or other identifiers. The Tool.name field is typed string with no pattern. A wrapper tool name such as mcp.wrapper is therefore unrestricted and compliant. A bare _meta key with no slash (e.g. mcpWrapper) is a name, not a prefix, so the reserved-prefix rule does not apply to it either.

Tool Result Shape

Source: 2025-06-18 server/tools; schema.ts CallToolResult.

  • content: ContentBlock[] — text / image / audio / resource link / embedded resource.
  • structuredContent? — optional structured JSON (new in 2025-06-18).
  • isError?: boolean — tool-level errors go here as true; absent means success.

Error split: errors from the tool (API failure, bad input) SHOULD be returned inside the result with isError:true. Errors in finding/dispatching the tool (unknown tool, unsupported call) SHOULD be a JSON-RPC protocol error. If a tool declares outputSchema, the server MUST return conforming structured results, and SHOULD also serialize them into a TextContent block for backward compatibility.

Proxy Obligations Summary

A transparent stdio proxy between an MCP client and server must preserve these invariants:

InvariantObligation
Request idRemap outbound ids consistently and restore the caller's id on response; never reuse an id within a session/direction.
_meta passthroughForward _meta unmodified both directions, including progressToken — stripping it breaks progress routing.
protocolVersionForward verbatim in initialize request and response; do not substitute a preferred version.
CapabilitiesDo not advertise what the backend lacks nor suppress what it declares; a self-owned, self-implemented capability is allowed.
CancellationTranslate requestId through the id remap; keep it direction-matched; never forward a cancel for a request not issued in that direction; never cancel initialize.
Notifications / responsesNever reply to a notification; absorb accidental echoes.
stdio framingUTF-8, newline-delimited, no embedded newlines; nothing non-MCP on stdout either direction.
DisconnectDo not convert a disconnect into a cancellation; require an explicit notifications/cancelled.
