Architecture

Scope

mcp-wrapper-rs is a stdio MCP wrapper. Its runtime contract is newline-delimited JSON-RPC over stdin/stdout on both sides: client to wrapper, wrapper to child MCP server. Streamable HTTP, OAuth, remote hosting, and multi-transport negotiation are outside the current architecture until a separate transport owner, schema, topology, and proof gate are added.

The project moved from one lightweight mixed proxy to owner-oriented modules. The primary product data is JSON-RPC messages and MCP tool/resource/prompt content. Backend lifecycle, daemon sockets, cache epochs, and logs are supporting state or evidence. The target shape is a data-owner map where primary data stays simple, every supporting state node has one owner, every crossing has one legal route, and every control action has readback evidence.

Architecture Thesis

stdio wrapper
-> JSON-RPC envelope owner
-> MCP tool/resource/prompt discovery owner
-> backend process owner
-> runtime or broker composition owner
-> hook/observe control plane
-> proof by tests, smoke, and readback

The wrapper should be smarter about backend state through hooks and observation, not through scattered direct wiring. Observation turns backend events into typed state. Hooks request a legal transition. Readback proves the new state before clients, logs, CLI projections, or MCP tool projections claim it.

Backend Lifecycle

Owned by backend_manager::BackendSlot. The slot owns the alive decision, the restart/stop transitions, and the lifecycle invariants; callers reach live state only through owner methods (live(), snapshot(), restart(), stop(), ensure()), never by locking the raw backend handle.

RuleBehaviour
Lazy spawnBackend created on first pass-through request, not at startup.
Retry3 attempts with exponential backoff on spawn failure, then degraded + cooldown.
Health checklive() returns the backend only if present and alive; dead backends map to a unavailable error.
Graceful shutdownSIGTERM, 5s wait, then SIGKILL.
Process group cleanupEach child in its own process group; child_pgids registry; killpg on exit.
Cache refresh on respawnSynchronous refresh (query all list/* from backend) before notifying clients, so clients never read stale cache.
Active-call gateStop and non-force restart are rejected while active calls exist. The invariant is owned by BackendSlot::{restart,stop}_blocked_by_active_calls; the active-call counter is owned by the caller (runtime_manager normal mode, broker_manager daemon mode).
Daemon init reuseDaemon/broker mode keeps the init backend alive instead of killing and re-spawning on first request.
Daemon no idle timeoutA broker spawned via --daemon runs until SIGTERM; idle timeout applies only to non-daemon relay mode.

Concurrency

  • Oneshot channels match request/response (client ID remapped to a monotonic backend ID, restored on response).
  • tokio::sync::Mutex guards backend access because the lock spans .await; child_pgids uses std::sync::Mutex because access is sync-only.
  • Bidirectional notification relay runs between client and backend.

Tools Projection

src/tools is the unified external tools window. It exposes exactly one wrapper-owned backend-visible tool, mcp.wrapper. CLI backend admin commands and MCP mcp.wrapper calls are interface projections into the same action schema and object-method dispatch layer.

tools/list
  -> backend cached tools + tools::catalog().mcp.wrapper

tools/call(name = "mcp.wrapper")
  -> tools::invoke(action, target, params, context)
  -> tools.object.method
  -> backend_manager | mcp_manager | broker_manager | daemon_manager owner API
  -> unified readback envelope

tools owns action names, input validation, descriptor generation, collision policy for the reserved mcp.wrapper name, and response envelope shape. It must not own backend lifecycle truth, discovery cache mutation, daemon socket state, or log identity. In daemon mode, mcp.wrapper receives broker-owned active-call readback before stop and non-force restart actions. Backend tools named mcp.wrapper are rejected before they can enter the merged tool table.

Validation is internalized into the invocation objects: ToolAction owns its action-specific param constraints (validate_params), and ToolInvocation::from_arguments owns the full invocation invariant — a successfully constructed invocation is always schema-valid. The free dispatch path only routes data into these objects; it holds no validation rules of its own.

The reserved mcp.wrapper descriptor and the tools capability are not merged per request. mcp_manager::Cache owns the lifetime of the external tools/list and initialize views as hold-state: they are rebuilt only when backend data loads or refreshes, so lookup is a pure read. The backend discovery fingerprint (discovery_hash) is computed from raw backend responses only and is never polluted by the wrapper-merged view.

Supervisor Registry Boundary

Multi-backend supervisor mode requires a registry owner before code. The registry owns backend identity, backend specs, route-table construction, collision state, and reload semantics. It does not replace backend_manager or mcp_manager; each registry entry points to one backend slot owner and one discovery cache owner.

SupervisorRegistry
  backendSpecs: backend id -> command, args, env projection, cwd, policy
  backendSlots: backend id -> backend_manager::BackendSlot
  discoveryCaches: backend id -> mcp_manager::Cache
  toolRoutes: backend tool name -> backend id
  wrapperRoute: mcp.wrapper -> tools object method
  collisions: tool name -> backend ids + policy state

The first registry implementation must fail closed on backend tool-name collisions. A stale or ambiguous route returns structured mcp.wrapper evidence instead of guessing at call time. Restarting one backend refreshes only that backend cache, then rebuilds the union route table and discovery hash.

Admin CLI Projection

The admin surface is a projection over the same tools object methods and hook/observe owners, not a second backend manager. Backend admin commands call mcp.wrapper through the broker JSON-RPC path and then project the wrapper envelope into CLI output. Broker metadata commands still use daemon_manager because broker socket and pid state are not backend tool state.

mcp-wrapper-rs status --json -- <command> [args...]
mcp-wrapper-rs backend status|ping|refresh|restart|stop --json -- <command> [args...]
mcp-wrapper-rs broker list|status|stop|restart --json -- <command> [args...]
mcp-wrapper-rs doctor --json -- <command> [args...]

CLI output is evidence projection. It must not directly mutate pid files, sockets, cache maps, or child processes except through daemon_manager, broker_manager, backend_manager, and mcp_manager APIs.

Daemon Boundary

Daemon mode is an optimization for sharing one backend among compatible wrapper sessions. It is safe only when the wrapped server can tolerate shared session/backend state. Stateful or per-client servers should use normal mode unless the server's own semantics explicitly allow sharing.

Server-to-client requests are request-scoped. The broker routes them to the active peer session and rejects unassociated backend requests instead of broadcasting them. Notifications can fan out only when the MCP method is a legal notification and cache readback has already been refreshed when required.

Change Rule

New behavior starts by naming the data node, owner, legal crossing, transition, and proof gate in the handbook. Code then becomes the executable projection. Tests prove the owner transform or composition boundary. Product code must not become a hiding place for durable tests, debug probes, or second control planes.
